# Auth, e-mail e abertura por ambiente

Abertura: `/zetta-estetica/launch` resolve os vínculos atuais; com um vínculo segue para a clínica, com vários abre o seletor. `/launch/:slug` mantém o destino após autenticação e só abre o vínculo permitido pelo banco. Consulta vazia não distingue clínica inexistente de acesso revogado/suspenso. Conta FLW e slug não autorizam acesso. Trocar slug exige nova resolução. `/` preserva o seletor anterior e o acesso ao console global.

Não há cadastro público. Mantenha **Allow new users to sign up desativado**, confirmação de e-mail ligada e `shouldCreateUser: false` no login OTP. Criação de identidade ocorre pelo Auth Invite no servidor, depois da autorização do convite no PostgreSQL. Uma identidade criada pelo Invite não recebe vínculo até aceitar o registro vigente com o mesmo e-mail confirmado. Identidade já existente entra por senha ou código de acesso e abre a rota do convite; não recriar usuário. Revogar convite ou vínculo não precisa excluir a identidade Auth: o banco nega a operação.

| Configuração | Local | Homologação/produção |
| --- | --- | --- |
| Site URL Auth | `http://localhost:5173/zetta-estetica/launch` | `<APP_URL>/launch`, URL HTTPS exata do ambiente aprovado |
| APP_URL no servidor | `http://localhost:5173/zetta-estetica` | Base HTTPS exata, sem query/fragmento/credenciais |
| APP_ORIGIN no servidor | `http://localhost:5173` | Origem exata de APP_URL |
| Redirects permitidos | `http://localhost:5173/zetta-estetica/convites/*` | `<APP_URL>/convites/*`; sem wildcard de domínio |
| Retorno FLW | vazio até aprovação; testes usam domínio `.invalid` | `VITE_FLW_RETURN_URL` HTTPS exata aprovada; rebuild por ambiente |
| SMTP | indisponível; envio OTP realmente falha | Provedor e domínio verificado do responsável; TLS, SPF/DKIM e DMARC configurados no provedor |
| Template | arquivos versionados em `supabase/templates/` | Aplicar os mesmos templates no Auth do projeto confirmado |

`supabase/config.toml` é a configuração local portável da CLI, não altera o GoTrue já em execução nesta stack sem Docker nem o projeto hospedado. O processo local mantém autoconfirm e os limites já fornecidos pelo ambiente; não representa confirmação por e-mail entregue. Para confirmar códigos nos testes, Admin gera material Auth exclusivamente de identidades sintéticas, e a verificação ocorre na API pública. Não imprimir código/hash/link/tokens como evidência.

No projeto confirmado, configurar no Auth **Magic Link** com `magic-link.html` (assunto “Seu código Zetta Estética”) e **Invite user** com `invite.html` (assunto “Seu convite Zetta Estética”). O primeiro usa `{{ .Token }}`, sem link de redirecionamento; o segundo usa Token e `{{ .RedirectTo }}` emitido pelo servidor a partir de APP_URL + UUID do convite. Não aceitar `redirect`, `next`, referrer ou `return` como destino externo. A Edge recusa APP_URL em origem diferente de APP_ORIGIN, credenciais, query, fragmento e HTTP fora de localhost. O retorno FLW da clínica armazenado pelo console anterior não é usado para navegar: só a configuração aprovada do build.

Configurar **Custom SMTP** com `SMTP_HOST`, porta TLS, usuário, senha, endereço remetente do domínio verificado e nome “Zetta Estética”, somente nos secrets/console Auth. Em CLI, aplicar por ambiente a seção `auth.email.smtp` com `enabled=true`, `host=env("SMTP_HOST")`, `port=587` (ou porta exigida pelo provedor), `user=env("SMTP_USER")`, `pass=env("SMTP_PASS")`, `admin_email=env("SMTP_ADMIN_EMAIL")` e `sender_name="Zetta Estética"`. O template base não habilita SMTP sem provedor. Configurar validade de código de 600 segundos, seis dígitos, intervalo mínimo de 60 segundos, limites de envio por IP e projeto e proteção antiabuso oferecida pelo provedor. Esses valores estão no config local; conferir/aplicar equivalentes no ambiente hospedado. Não copiar o autoconfirm local para produção.

Antes de publicar, confirmar ref/URL/ambiente com o responsável; a base Pages informada é `https://adilsonzetta.github.io/zetta-estetica`, ainda sem comprovação de Auth/FLW nesta etapa. Conferir compatibilidade entre URL publicada, APP_URL, APP_ORIGIN, allowlist Auth e domínio remetente. Não aplicar bootstrap, fixtures ou chaves locais no hospedado.

O código é uma credencial temporária: não encaminhar. Outra conta autenticada não pode aceitar um convite encaminhado; quem receber também o código pode representar a identidade convidada até expiração/uso, como em qualquer OTP. Revogação do convite ainda impede vínculo, inclusive com sessão Auth válida. Aceite é idempotente enquanto o vínculo e o convite permanecem válidos; repetição após revogação não reativa acesso. Erros de código expirado/reutilizado e de convite revogado/expirado orientam novo envio/revisão administrativa, sem revelar detalhes a terceiros.

Mudança de rota/identidade desmonta o estado anterior; consultas de contexto recebem AbortSignal, previews Blob registrados são revogados e canais Realtime são removidos. Não há cache persistente de dados de tenant. A sessão Auth é persistida pelo SDK, não os dados clínicos. Ao voltar o foco ou a cada 60 segundos em launch/clínica, a interface descarta o contexto e reconsulta o banco. Isso também reinicia formulários locais desse contexto; novas operações são sempre autorizadas no banco, mesmo antes desse intervalo. Não há documentos clínicos implementados nesta etapa; futuros previews/recursos devem usar o registro em `src/context.ts`.

Iframe permanece fechado: o app mostra apenas “Abrir em aba externa” e não instancia cliente Auth dentro do frame. Não há postMessage, SSO ou liberação por referrer/conta FLW. O console registra modo desejado, status, instalador autenticado e evidência redigida; essas anotações não ativam capacidades. Para futura habilitação de iframe, exigir teste de sessão/cookies e persistência desktop/Android/iOS, origens exatas e CSP `frame-ancestors` no host que permita configurá-la, com fallback externo. SSO exige contrato oficial e prova formal em duas contas, registrados como evolução.
